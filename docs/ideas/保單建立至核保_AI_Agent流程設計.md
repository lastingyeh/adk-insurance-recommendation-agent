# 保單建立至核保全流程之 AI Agent 賦能設計
### 合規、可控、可規模化的內部作業優化藍圖

> 本設計延續前篇「OKF / Harness / Agent / Testing & Evaluating / Loop / Go Flow-Product」六大構面，將其落地為一套具體的保險內部作業流程：**從要保書建立到核保決議完成**。全文以 5W1H 拆解每個階段的痛點與對應解法，最後提出後續框架搭配建議（ADK、Codex、Claude Code / Claude Agent SDK）。

---

## 〇、設計總則：六大構面如何對應到核保場景

| 構面 | 在核保流程中的角色 |
|---|---|
| **OKF（知識層）** | 把核保規則、商品條款、法遵條文、既往病史對照表整理成結構化知識庫，讓 Agent 每次核保都能穩定取用同一套「權威事實」，而不是每次重新檢索或憑模型記憶臆測 |
| **Harness（行為框限層）** | 定義核保 Agent 能做什麼、不能做什麼——例如「可以初篩、不能核准」「金額超過門檻必須轉人工」——用規則檔、工具白名單、護欄把風險鎖在可控範圍 |
| **Agent（自主性光譜）** | 依風險等級把不同子流程放在光譜的不同位置：標準案件高自主性、高風險或高保額案件低自主性、人類保留核決權 |
| **Testing & Evaluating（驗證層）** | 測試處理確定性規則（保費試算、年齡限制）；評估處理非確定性判斷（病歷摘要品質、拒保理由是否合理） |
| **Loop（自動迭代層）** | 用於補件催收、文件重新驗證、複核意見回饋等「有明確完成標準」的重複性任務 |
| **Go Flow → Go Product（產線化）** | 把整條核保流程當成一條裝配線來設計：人類負責定義規格與限制條件，Agent 負責在限制內執行，品質門檻決定何時放行、何時升級 |

## 一、全流程架構總覽

```
① 要保書建立
   └─(資料蒐集：身分/財務/健康告知)
② 文件結構化與驗證（OCR + OKF 比對）
   └─(身分核實、既往病史比對、既有保單查核)
③ 風險初篩 Agent（規則引擎 + LLM 判讀）
   └─(標準件 / 次標準件 / 高風險件 分流)
④ Harness 護欄與升級判斷
   └─(是否超過自動核保門檻？是否觸發法遵警示？)
⑤ 人工複核（僅限被升級案件）
   └─(核保人員審閱 Agent 摘要 + 完整佐證資料)
⑥ 核保決議與保單條件生成
   └─(核准 / 加費承保 / 除外承保 / 拒保)
⑦ 保單簽發與稽核留存
   └─(生成保單、留存決策軌跡、回饋 Loop)
```

## 二、逐階段 5W1H：痛點到解決方案

### 階段① 要保書建立與資料蒐集

| 5W1H | 現況痛點 | AI 解決方案 |
|---|---|---|
| **Who（誰）** | 業務員手動抄錄要保人資料，易漏填、易謄寫錯誤；客戶需重複填寫多份表單 | 由對話式 Agent 直接引導要保人／業務員完成資料蒐集，即時做格式與邏輯檢查 |
| **What（什麼）** | 紙本／PDF 掃描件、健康告知書格式不一，後端系統難以直接消化 | Agent 將輸入即時轉為結構化資料，並比對 OKF 知識庫中的商品規則（承保年齡、告知事項清單） |
| **When（何時）** | 資料缺漏往往到核保階段才被發現，來回補件耗時數天 | 在「填寫當下」即時驗證必填欄位與邏輯一致性（例如告知疾病與投保金額的合理性） |
| **Where（何地）** | 業務員現場、客服電話、線上投保入口三種管道資料格式不同 | 統一透過同一個 OKF 結構化 schema 收斂三種管道的輸出，後端核保引擎不需為每個管道客製 |
| **Why（為何）** | 前端資料品質差，直接拖垮後端核保效率與正確率 | 提高「一次到位」比例，減少後續補件與人工來回溝通成本 |
| **How（如何）** | — | 用一個輕量對話 Agent（低自主性、僅能讀寫表單欄位，不能做核保判斷）作為前端守門員，搭配 OKF 商品規則庫做即時規則校驗 |

---

### 階段② 文件結構化與驗證（OCR + OKF 比對）

| 5W1H | 現況痛點 | AI 解決方案 |
|---|---|---|
| **Who** | 核保助理人力大量花在「把紙本病歷、健檢報告轉成可讀資料」 | OCR + 文件理解 Agent 自動抽取關鍵欄位（診斷、用藥、檢驗數值） |
| **What** | 病歷用詞、機構格式差異大，抽取正確率不穩定 | 抽取結果與 OKF 醫學知識庫（ICD 對照、常見既往病史風險分級）比對，標記信心分數 |
| **When** | 文件驗證是「一次性」動作，發現漏頁或影像不清只能事後補件 | 在文件上傳當下即做完整性檢查（頁碼連續性、關鍵欄位是否可辨識），不完整立即提示重新上傳 |
| **Where** | 文件散落在案件系統、Email、掃描機三處，版本容易搞混 | 所有文件統一寫入 OKF 目錄結構（`/cases/{case_id}/documents/`），保留來源與版本紀錄 |
| **Why** | 抽取錯誤會直接污染下游風險初篩的判斷基礎 | 用信心分數機制，把低信心欄位自動路由給人工確認，而非讓錯誤資料無聲流入核保引擎 |
| **How** | — | Harness 規則：OCR Agent 只有「讀取與標記」權限，任何欄位改寫都需寫入稽核軌跡；低於信心門檻者強制人工複核 |

---

### 階段③ 風險初篩 Agent（規則引擎 + LLM 判讀）

| 5W1H | 現況痛點 | AI 解決方案 |
|---|---|---|
| **Who** | 資深核保人員稀缺，初階案件也要排隊等資深人員判斷，產能受限於人力 | 風險初篩 Agent 承擔「標準案件」的初判，資深核保人員專注在真正需要判斷力的案件 |
| **What** | 既往病史、財務狀況、保額三者需交叉判斷，人工判斷標準不一致（同案不同核保人員結論不同） | Agent 依 OKF 核保規則手冊（風險分級表、加費係數表）做一致性判斷，並附上判斷依據引用 |
| **When** | 案件在核保佇列中平均等待數日才被翻閱 | Agent 於文件驗證完成後即時初判，秒級完成標準案件分流 |
| **Where** | 判斷邏輯散落在資深核保人員腦中、內部教育訓練投影片、零散的內部備忘錄 | 這些隱性知識預先轉譯進 OKF 知識庫（成為所有 Agent 與新進核保人員共用的權威來源） |
| **Why** | 不一致的核保標準是法遵與申訴風險的來源 | 用同一套結構化規則做初判，提升核保結論的一致性與可解釋性 |
| **How** | — | Agent 產出「初判結果 + 引用的規則條目 + 信心分數」三件套，而不是只給結論；Harness 限制 Agent 只能「建議」，核准／拒保的最終決定權留給下一階段的門檻判斷或人工 |

---

### 階段④ Harness 護欄與升級判斷（自動核保 vs 轉人工）

| 5W1H | 現況痛點 | AI 解決方案 |
|---|---|---|
| **Who** | 目前「哪些案件該轉人工」高度依賴個別核保人員經驗，標準不透明 | 用明確、可稽核的門檻規則取代個人經驗判斷：保額門檻、既往病史風險等級、法遵紅旗清單 |
| **What** | 高風險案件與標準案件混在同一條佇列，資深人力被稀釋在大量標準案件上 | Harness 依風險分級自動分流：標準件走高自主性自動核保，高風險 / 高保額 / 觸發法遵警示件強制降低自主性、轉人工 |
| **When** | 升級（escalation）判斷往往在案件已經走了大半流程後才發生，浪費前面的處理時間 | 升級判斷點前移到初篩完成的當下，一次決定路徑，避免案件在系統裡來回 |
| **Where** | 升級規則寫死在核保人員的經驗與零散的內部 SOP 文件裡 | 升級規則同樣寫入 OKF 知識庫並版本控制，任何規則調整都可追溯、可回溯測試對既有案件的影響 |
| **Why** | 沒有明確護欄，Agent 的自主性擴張會直接變成法遵與財務風險 | Harness 是把「Agent 能做到多自主」這個問題，轉成一個可以被治理、被稽核的工程設計問題 |
| **How** | — | 具體護欄範例：①保額超過 NT$X 萬強制人工；②告知事項命中高風險 ICD 碼強制人工；③ Agent 拒保建議一律強制人工複核（避免自動化拒保引發申訴與品牌風險）；④任何 Agent 判斷都須寫入不可竄改的決策軌跡（audit log） |

### 階段⑤ 人工複核（僅限被升級案件）

| 5W1H | 現況痛點 | AI 解決方案 |
|---|---|---|
| **Who** | 核保人員複核時要從頭翻閱所有原始文件，效率低 | Agent 預先產出「案件摘要 + 風險亮點 + 引用規則 + 建議選項」，核保人員從審閱摘要開始，需要時再下鑽原始文件 |
| **What** | 複核意見多半只存在核保人員的口頭或簡短備註中，難以沉澱成組織知識 | 複核人員的修正意見（同意 / 修改 / 推翻）結構化記錄，成為 OKF 知識庫與未來評估集的養分 |
| **When** | 複核排程與案件到達速度不同步，容易塞車 | 依風險等級與 SLA 動態排優先序，高保額／高風險案件優先進複核佇列 |
| **Where** | 複核工作台與初篩系統是兩套介面，資訊要來回切換查詢 | 統一工作台呈現：Agent 摘要、原始文件、OKF 規則引用、歷史類似案例，全部在同一畫面 |
| **Why** | 人工複核是整條流程中最珍貴、也最貴的資源，必須被用在刀口上 | 把複核人員的時間集中在「真正需要判斷力」的案件，而非重複性的資料核對 |
| **How** | — | 複核人員的每一次「推翻 Agent 建議」都視為一筆評估樣本，定期回饋進 Testing & Evaluating 的評估集，用來偵測 Agent 的系統性誤判模式 |

### 階段⑥ 核保決議與保單條件生成

| 5W1H | 現況痛點 | AI 解決方案 |
|---|---|---|
| **Who** | 決議理由的書面說明常常是核保人員事後補寫，用詞前後不一致 | Agent 依決議類型（核准／加費／除外／拒保）自動生成結構化理由書初稿，人員審閱後定稿 |
| **What** | 加費係數、除外條款的套用容易因人工疏漏而不一致 | 條件生成直接引用 OKF 規則庫的係數表與條款範本，避免手動計算錯誤 |
| **When** | 決議理由的完整性審查往往在申訴發生時才被回頭檢視 | 每筆決議在生成當下就完成理由完整性檢查（是否引用規則、是否附證據），而非事後補救 |
| **Where** | 理由書散落在案件系統的自由文字欄位，難以結構化查詢 | 理由書以結構化格式（決議類型、依據條文、係數計算式）存入案件紀錄，可查詢可統計 |
| **Why** | 決議理由的品質直接影響法遵抗辯能力與客訴處理效率 | 一致、可追溯的理由書，是合規稽核與監理機關查核時最直接的防護 |
| **How** | — | Harness 規定：任何「拒保」或「加費」理由都必須包含至少一條 OKF 規則引用，缺少引用則該筆決議無法送出，強制觸發人工補充 |

### 階段⑦ 保單簽發與稽核留存

| 5W1H | 現況痛點 | AI 解決方案 |
|---|---|---|
| **Who** | 稽核／法遵人員事後抽查，樣本覆蓋率有限 | 全案件留存決策軌跡，稽核可對 100% 案件做自動化合規掃描，而非僅抽樣 |
| **What** | 品質退化（模型改版、規則調整後核保品質下降）不容易被即時發現 | 持續評估管線比對新舊版本在既有案件集上的判斷差異，異常波動自動告警 |
| **When** | 系統性錯誤往往要累積到客訴或監理質詢才被發現 | Loop 機制定期重跑既有測試案件集（回歸測試），任何規則或模型更新都先過這道關卡才能上線 |
| **Where** | 稽核留存資料格式不一，查詢跨系統資料困難 | 決策軌跡、引用規則版本、複核修正紀錄，統一寫入 OKF 結構化紀錄，供稽核與監理報送直接查詢 |
| **Why** | 保險核保是高度受監理的領域，可解釋性與可追溯性本身就是合規要求 | 把「合規」內建在流程設計裡，而不是事後补文件 |
| **How** | — | 每張保單簽發都附帶一份不可竄改的「決策卡」：初判結果、引用規則版本、是否經人工複核、複核人員、最終決議依據 |

## 三、Harness 護欄設計重點（跨階段共通）

1. **權限分級**：初篩 Agent 只能「建議」，不能「核准」；文件 Agent 只能「讀取標記」，不能「改寫原始資料」。
2. **強制升級條件**：保額門檻、高風險病史、法遵紅旗、Agent 建議拒保，四類情境一律轉人工，不允許全自動放行。
3. **引用強制**：任何影響核保結論的判斷，都必須附上可追溯的 OKF 規則版本引用，沒有引用即視為不完整輸出。
4. **不可竄改稽核軌跡**：每個 Agent 動作（讀取、標記、建議、升級）都寫入唯讀的稽核日誌，供法遵與監理查核。
5. **錯誤即進化**：每一次人工複核推翻 Agent 建議，都回饋進規則庫或評估集，而不是被當成單次個案結案了事。

## 四、Testing & Evaluating 設計重點

| 驗證類型 | 對應項目 | 說明 |
|---|---|---|
| **測試（確定性）** | 保費試算、年齡／保額上下限、必填欄位邏輯 | 給定輸入應得到唯一正確輸出，用單元測試持續守住 |
| **評估（非確定性）** | 病歷摘要品質、拒保理由合理性、風險分級判斷 | 用核保人員的歷史決議作為黃金標準集，定期比對 Agent 判斷與人工判斷的一致率 |
| **影子部署** | 新規則 / 新模型版本 | 先在既有案件集上跑影子評估，確認品質不退化才切換正式流量 |
| **持續監控** | 人工複核推翻率、升級案件比例、各風險分級的通過率 | 這些指標的異常波動，往往是規則庫過時或模型漂移的早期信號 |

## 五、Loop 設計重點：哪些任務適合自動迴圈

- **補件催收**：文件不完整時，Agent 自動生成補件通知、追蹤補件狀態、補齊後重新觸發驗證，一個任務一輪、直到補件完成或逾期升級人工。
- **文件重新驗證**：OCR 信心分數不足時，重新請求清晰版本、重跑抽取，直到達到信心門檻或達到重試上限後轉人工。
- **回歸測試迴圈**：規則庫或模型每次更新，自動在既有案件回歸集上重跑評估，直到通過品質門檻才允許上線（可視為核保領域的 Ralph Loop）。
- **複核意見回饋迴圈**：人工複核修正意見定期彙整，Agent 自我檢視系統性誤判模式並提出規則庫修訂建議，交由法遵與核保主管審核後才真正更新知識庫（避免規則不受控地自我演化）。

## 六、預期效益

**效率面**
- 標準案件初判從「天」級降到「秒 / 分」級，資深核保人力集中在高風險判斷。
- 補件來回從多輪人工溝通，收斂為系統自動催辦，縮短案件平均週期。

**品質與一致性面**
- 核保判斷依據同一套結構化規則庫，降低「同案不同核保人員不同結論」的落差。
- 決議理由結構化、強制引用規則，降低申訴時「說不清楚為什麼拒保」的風險。

**合規與可稽核面**
- 100% 案件留存決策軌跡，稽核從抽樣走向全量，監理報送資料可直接查詢。
- 品質退化可被持續評估管線即時偵測，而非等到客訴或稽核才發現。

**組織知識沉澱面**
- 資深核保人員的隱性判斷邏輯，透過 OKF 知識庫沉澱成組織資產，降低關鍵人力流失的風險。

## 七、後續框架搭配建議

## 八、治理與風險提醒

1. **人在迴圈是不可退讓的底線**：拒保、加費、高保額案件的最終核決權，設計上必須保留給人類核保人員，Agent 的角色是「建議者」而非「決策者」。
2. **知識庫的變更管理**：OKF 規則庫的任何修訂，都應經過法遵與核保主管審核，並保留版本歷史，避免規則被「自我演化」的迴圈悄悄改動而未被察覺。
3. **模型與框架都會迭代**：本設計中列出的 ADK、Codex、Claude Code 相關能力持續快速演進，實際導入前應覆核官方文件確認當下版本的功能與合規適用性，而非以此文件內容為最終依據。
4. **資料隱私與資安**：健康告知、病歷等屬敏感個資，文件 Agent 的存取範圍、資料保存期限與加密方式，需另行納入資安與個資保護的合規審查範疇，本文不涵蓋該部分細節設計。
